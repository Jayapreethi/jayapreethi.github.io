Containerized ML Is Not the Same as Reproducible ML

Containers help preserve software environments, but scientific AI results also depend on hardware, numerical behavior, runtime choices, workflow provenance, and validation.

May 2026 · Scientific ML · HPC · AI Infrastructure
AI Reproducibility Scientific ML HPC Containers ML Workflows

The core problem

Containerization has become one of the most useful practices in modern machine learning and scientific computing. Docker, Singularity, and Apptainer help researchers package code, libraries, and runtime environments so experiments are easier to move across laptops, institutional clusters, cloud systems, and HPC environments.

That is a major improvement over the old “works on my machine” problem. But there is an important distinction that often gets blurred.

A container can help reproduce a software environment. It does not automatically reproduce a scientific result.

For research teams working with deep learning, physics-informed models, simulation workflows, or large-scale HPC systems, this distinction matters. Two experiments can use the same code, the same container image, and the same dataset, yet still produce different results because numerical behavior, hardware execution, runtime library choices, and workflow decisions may not be fully controlled.

What containers do well

Containers are valuable because they make software environments more portable and easier to inspect. They can help teams preserve package versions, system libraries, directory structure, configuration files, runtime dependencies, and the basic execution environment.

For many engineering workflows, that is enough to make deployment more predictable. For scientific machine learning, it is necessary but not sufficient.

Same environment is not always same result

A container answers one question well: can someone run this code in a similar software environment? Scientific reproducibility requires more: whether the result remains stable across repeated runs, whether it holds across hardware platforms, and whether small numerical differences change the scientific conclusion.

In deep learning, small numerical differences can sometimes accumulate during optimization. In many cases, the final answer may still be scientifically consistent. In other cases, differences in precision, GPU kernels, reduction order, or nondeterministic operations can affect convergence behavior, evaluation metrics, or model selection.

Where reproducibility can still break

1. Dependency specifications may be incomplete

A Dockerfile or container recipe may appear precise while still leaving important details unresolved: base image digest, cuDNN point release, cuBLAS or NCCL version, compiler options, GPU architecture, and transitive Python dependencies.

2. GPU libraries make runtime decisions

Modern GPU libraries are optimized for performance. They may choose algorithms dynamically based on tensor shapes, available memory, device architecture, benchmarking settings, and other runtime conditions. Different low-level execution paths may be mathematically equivalent in exact arithmetic, but floating-point arithmetic is not exact.

3. Floating-point differences can accumulate

Floating-point arithmetic depends on operation order, data type, hardware implementation, and parallel reduction behavior. In large-scale training, these effects can influence loss curves, convergence timing, and occasionally model selection.

4. Workflow provenance is often incomplete

Reproducibility is not only about rerunning the final script. Scientific workflows involve exploration: data cleaning, feature engineering, failed experiments, hyperparameter search, simulation-based validation, and threshold decisions used to select final results.

A practical checklist

  • Use immutable container image digests when possible.
  • Pin direct and transitive dependencies.
  • Record CUDA, cuDNN, cuBLAS, NCCL, compiler, and driver versions.
  • Record GPU model, compute capability, memory, and driver version.
  • Save runtime logs at the beginning of each experiment.
  • Record precision settings such as FP32, TF32, BF16, or FP16.
  • Run more than one seed for publication-quality claims.
  • Validate not only predictive accuracy, but also domain consistency.

The path forward

Perfect bitwise reproducibility may not always be realistic for modern ML systems, especially at scale. But that should not be the only standard.

A more useful goal is robust scientific reproducibility: results that are stable enough, documented enough, and validated enough for others to build on.

Containerization captures the software environment. Reproducibility requires control, documentation, and verification across the entire stack.
